Ashley Bridge 5.0.0: store assets

Brought up to date 2026-09-29 for 5.0.0, after the agreement became version 5 (LICENSE.txt version 5, PRIVACY.md
version 6, TERMS_VERSION 5). Five screenshots come from 5.0.0 release builds: 02 and 04b from run D2 (22:23 to 22:24
UTC), and 01, 01b and 05 from run E (22:47 to 22:51 UTC), taken from the release build rebuilt with agreement version 5
because they show the agreement's version or its hashes. These are the only images whose content changed (see "Which
images changed" below). The other four (03, 03b, 04, 05b) are the 4.0.0 images of 19:03 to 19:08 UTC, kept because
what they show is the same in 5.0.0.

How the 5.0.0 images were made (runs D2 and E, e2e/run-D2-own-copy-reviewer-recipe-st1234.txt and
e2e/run-E-agreement-v5-reviewer-recipe-st1234.txt): the real release build (extension/.output/chrome-mv3, 5.0.0,
framework 5 bundled; for run E the build that ships LICENSE.txt version 5 and PRIVACY.md version 6) loaded into
Playwright's Chromium (Chrome for Testing 153) with a fresh profile, a 1280x800 viewport and the light colour scheme,
driven against the mock Open OnDemand portal (extension/mock-ood/server.mjs) served over https at localhost:8443 with a
self-signed certificate, exactly as the store reviewer's recipe runs it: --user st1234 and MOCK_LOGGED_IN=false, the
mock's own home seeding (since 5.0.0 the mock's command line sets its stand-in tool up as the account's own copy at the
version the build carries, so the strip finds the tool installed and uploads nothing; Details reads "tool: your copy,
version 5"). There is no key: the extension read the account name the mock's dashboard shows and asked the real
access service, which answered approved:true for st1234. The agreement was accepted on the setup page as a person
does (scrolled to the end, four boxes ticked, a typed name, "Accept and Continue"); in run E, 01 was taken before
anything was touched and 01b once the four boxes were ticked and the name typed, before the button was pressed (no
request had gone to the vendor by then). The toolbar button was pressed on the portal tab with the DevTools
protocol's Extensions.triggerAction (the action a click runs), and the browser's own permission prompt was answered
with Windows UI Automation (its Allow button); no extension state was edited. Before that click the side panel was
switched off with chrome.sidePanel.setOptions, so the background's own fallback opened the strip as a tab, which is
what is captured at 1280x800; in Chrome and Edge a person sees the same strip in the side panel beside the portal.
Nothing in the images was drawn by hand or composited. Each image was looked at, and the harness checked each page's
text (in run E, the text on screen): no machine path and no personal name appears in any of them.

Which images changed in 5.0.0, and how that was decided
- 04b: the new line naming the copy of the tool the account runs ("tool: your copy, version 5"), and check 6's new
  ending. 02: check 6 now says which copy is installed ("(your own copy)").
- 01, 01b, 05: the agreement is version 5 and the privacy statement version 6. 01's dialog heading and 01b's first
  statement name version 5; 05's acceptance card reads "Accepted version 5" and carries the new texts' SHA-256
  prefixes (05 had already been taken again in run D2 for the reworded privacy statement, when the agreement was
  still version 4). 01b now shows the dialog completed (boxes ticked, name typed, the button enabled) where the 4.0.0
  image showed it untouched.
- 04, 05b: taken again in run D2 as candidates and compared with the 4.0.0 images. 04 shows the same words (the
  pixels differ only in rendering); 05b's settings are the same and its audit rows are the run's own requests at any
  time. Run E took 05b again as a candidate: it shows no version string (no agreement version, hash or product
  version), so the 4.0.0 image stays. 03 and 03b show steps 5.0.0 did not change (the sign-in step, the statement
  step), so they were not taken again.

Caveats
- The strip is captured as a tab, not in the side panel (see above); the content is the same page.
- The agreement text inside the dialog names the licensor (the copyright line and the parties clause of
  LICENSE.txt, the first lines of PRIVACY.md); neither is inside the visible part of 01 or 01b (01 shows only the top
  edge of the full-text box, 01b none of it).
- 02, 04b: "Connected - phone - HEAD" and "student@example.edu" are the mock's stand-in Remote Control and
  Claude sign-in values, not the reviewer's or anyone's account.
- 04, 03: the claude.ai tabs the extension opened during the runs (the mock's sign-in URL with a mock client id,
  and the mock's environment link) loaded claude.ai itself; the harness stubbed their assets only (the e2e logs
  say which requests). They are not in any image.
- The time stamps in 02, 04b and 05 are this machine's local time (US Eastern) as the extension shows them; the
  "checked ... UTC" in check 1 and the access card is UTC.
- Run C sent the real access service one check with the portal name "ondemand.wayne.localhost" for st1234 (the
  store reviewer's mock username); the service keys its answer on the account name only.
