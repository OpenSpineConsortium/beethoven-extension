Ashley Bridge 3.0.0: store assets

Made 2026-09-29 (screenshots recaptured the same day after review; the three rendered images are from the
first capture). The screenshots are the real built extension (extension/.output/chrome-mv3, the 3.0.0 release
build that the store zips are made from) loaded into Playwright's Chromium (Chrome for Testing) with a
1280x800 viewport, light colour scheme, driven against the mock Open OnDemand portal (extension/mock-ood/server.mjs)
served over https on localhost with a self-signed certificate, the mock user st1234, MOCK_LOGGED_IN=false so
the Claude sign-in step is reached, and a three-day trial key issued for that username with the vendor tool.
The mock home was seeded with .hpcworker/profile.json and .hpcworker/VERSION = 2 so the strip found the tool
installed at the bundled version. The mock's seeded tool printed and recorded the portal's own home,
/home/st1234, in place of the mock home's real path (the mock's MOCK_DISPLAY_HOME knob, which server.mjs sets
to the virtual home by default; --display-home DIR overrides it), so the strip's grey output box shows the path
a cluster user would see. The withdrawn-keys list was fetched by the extension itself from
https://openspineconsortium.com/ashley/bridge-killlist.json once the agreement was accepted (the list issued
2026-09-29 15:32 UTC, nothing withdrawn); no other request left for the maintainer's site, and none went to
Anthropic: every claude.ai / claude.com navigation was answered locally by the test harness. The browser's
native permission prompt was accepted through Windows UI Automation (the Allow button), not by editing any
state. Nothing in the images was drawn by hand or composited. After each capture the whole page's text was
checked for a machine path, a username or a neighbouring project's name; none was found (see the note on 01).

Note on 01 and 01b: the agreement text in the dialog names the licensor ("Copyright (c) 2026 Gregory Schwing,
trading as OpenSpineConsortium"), as LICENSE.txt does; that is the contract's own text, not a machine detail.
Note on 01b-agreement-statements.png: the licence card below the dialog names wayne.edu as its example of
a site-key domain (extension source, src/ui/options.ts). Prefer 01 for the stores unless that example is
changed; the product itself carries no university name.
Note on 05-setup-page.png: captured from "3. Your portal" down. The page top after setup shows the saved key in
the input field in the clear, so it is not captured; 01 shows the page top before setup.
Note on 02-checks.png: check 1 reads "kill-list of 2026-09-29" and OK. On the first run of the checks in this
fresh browser it read WARN although the list was already on file: check 1 also warns while the username it
matched the key to was typed rather than seen on the portal's dashboard, and the dashboard's username is put
on record by check 4 of the same run (src/core/checks.ts), so the first run warns once and the next is OK.
The image is the second run, 82 s after the first.
Note on the grey output box in 03, 03b and 04: it is the strip's own output box showing the last shell
command's output (the mock's probe submission). The mock tool now prints the portal's home (/home/st1234) in
place of the mock home's real path (see above); against a real portal the box shows the cluster's path.
Nothing was hidden or cropped.
Note on 04b-details-worker-card.png: the strip's notice line ("Running the checks...") stays after a Details
action until the next one, so the image was taken from the panel reopened after the checks (the report is
kept in session storage and is the same one as in 02).
