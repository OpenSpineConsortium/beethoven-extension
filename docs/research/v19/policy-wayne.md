
## findings

### 1
**question**: 1a. Chrome Web Store: does a password for another site count as personal or sensitive user data, and what is the minimum duty?
**answer**: Yes. The User Data FAQ lists 'Authentication information (such as logins, password, and authentication cookies)' as personal or sensitive user data. Handling it means at least a privacy policy in the Developer Dashboard and secure handling. Storing it only on the device still counts: FAQ 14 says local-only storage needs a privacy policy too.
**verdict**: confirmed
**evidence**: https://developer.chrome.com/docs/webstore/program-policies/user-data-faq. The site is blocked from this session, so the text was read from Google's own page source, https://raw.githubusercontent.com/GoogleChrome/developer.chrome.com/main/site/en/docs/webstore/program-policies/user-data-faq/index.md (front matter 'updated: 2023-05-01'). Q3: "Health information, Authentication information (such as logins, password, and authentication cookies)". Q2: "by 'handle' we mean collecting, transmitting, using, or sharing user data", including "Having login functionality (even if you use a third-party system, like Google authentication)". Q5: "Products that handle personal or sensitive user data must, at a minimum: - Post a privacy policy in the Chrome Web Store Developer Dashboard, and - Handle the user data securely, including transmitting it via modern cryptography." Q14 (local-only storage): "Yes. This policy requires all Products that handle sensitive user information to post a privacy policy. Users may not easily be able to tell which apps or extensions save information locally or transmit it back to their servers."

### 2
**question**: 1b. Chrome Web Store: prominent disclosure and affirmative consent
**answer**: These are required only when the handling is 'not closely related to functionality described prominently' on the store page and in the extension's interface. When they apply, the disclosure must be inside the extension's own interface. A privacy policy, terms or the store description is not enough on its own, and the user must take a specific action to agree before anything is collected. A password feature that the listing and the panel describe prominently may fall outside this rule. The safe reading is still an in-panel disclosure plus an unticked box or press before the first save, which fits the repository's own 'never pre-tick' rule.
**verdict**: confirmed
**evidence**: https://developer.chrome.com/docs/webstore/program-policies/disclosure-requirements (source: raw.githubusercontent.com/GoogleChrome/developer.chrome.com/main/site/en/docs/webstore/program-policies/disclosure-requirements/index.md, date 2022-11-01): "If your Product handles any user data that is not closely related to the functionality described prominently in the Product's Chrome Web Store page and user interface, then prior to installation, it must: Prominently disclose what user data will be collected and how it will be used; Obtain the user's affirmative and informed consent for such use". User Data FAQ Q9: "These requirements only apply when both: The Product handles personal or sensitive user data AND The handling ... is not closely related to functionality described prominently in the Product's Chrome Web Store page and user interface." Q10: "The disclosure, however, must not be located only in a privacy policy, terms of service, or similar document. To obtain consent, the Product must ask the user to agree to the prominent disclosure in a manner that requires them to take a specific action clearly agreeing to the disclosure before collecting or using the personal or sensitive user data. The prominent disclosure and consent must occur within the Product's user interface. Disclosures in the Chrome Web Store description or inline installation page do not satisfy this requirement."

### 3
**question**: 1c. Chrome Web Store: secure handling, encryption at rest and in transit
**answer**: User data must be sent over HTTPS or WSS. The FAQ also says personal and sensitive data must be 'stored at rest using a strong encryption method such as RSA or AES'. The Handling Requirements add 'Keep authentication information secure. Don't publicly disclose authentication information.' A grid password kept in the extension therefore has to be encrypted at rest. A plain string in chrome.storage.local does not meet FAQ 8.
**verdict**: confirmed
**evidence**: https://developer.chrome.com/docs/webstore/program-policies/data-handling (source: .../program-policies/data-handling/index.md, date 2022-11-01): "If your product collects any user data, it must handle the user data securely, including transmitting it via modern cryptography." and "Keep authentication information secure. Don't publicly disclose authentication information." A web search on 2026-10-09 returned the live page with the same items. User Data FAQ Q8: "Extensions must transmit \"personal and sensitive user data\" over a secure connection (e.g. HTTPS, WSS) and stored at rest using a strong encryption method such as RSA or AES. You should not use any cipher suite that is denylisted by IETF. Our requirements may change over time." Q11: "The Other Requirements section prohibits publicly disclosing authentication, payment, or financial information".

### 4
**question**: 1d. Chrome Web Store: Limited Use requirements
**answer**: Use is limited to the practices disclosed and to the single purpose. Data goes to third parties only when that is necessary for the purpose, required by law, for fraud or abuse protection, or in a merger with prior consent. People may not read the data except with the user's explicit consent, for security or for legal reasons. A website statement of compliance is required, and Beethoven already publishes one (docs/store/LISTING.md line 279). FAQ 15 says Limited Use does not apply to data a client sends to a server the user specified. That may cover sending the password to the student's own portal, but the secure-handling rules still apply. Applying FAQ 15 to Beethoven is my reading, not Google's statement.
**verdict**: confirmed
**evidence**: https://developer.chrome.com/docs/webstore/program-policies/limited-use (source: .../program-policies/limited-use/index.md, date 2022-11-01): "You must limit your use of the data to the practices you disclosed." "Limit your use of user data to providing or improving your single purpose" "Only transfer user data to third parties: If necessary to providing or improving your single purpose; to comply with applicable laws; to protect against malware, spam, phishing, or other fraud or abuse; or, as part of a merger..." "Do not allow humans to read user data, unless: the user's explicit consent to read specific data ... is obtained; ..." "An affirmative statement that your use of the data complies with the Limited Use restrictions must be disclosed on a website belonging to your extension". User Data FAQ Q15: "When the Product is a client for an internet protocol with user-specified servers, like an FTP or IRC client, the Limited Use section does not apply to the Product's collection of data for, or transmission of data with, the user-specified server."

### 6
**question**: 1f. Chrome Web Store: permissions and review
**answer**: The store asks for the narrowest permissions. Broad host access and sensitive permissions lengthen review, and the review page names 'harvest credentials' as a reason. Answering onAuthRequired in MV3 needs two more permissions, webRequest and webRequestAuthProvider (see 3e). Beethoven's broad optional https://*/* host pattern is already in the category Google flags.
**verdict**: confirmed
**evidence**: https://developer.chrome.com/docs/webstore/program-policies/permissions (source: .../program-policies/permissions/index.md): "Request access to the narrowest permissions necessary to implement your Product's features or services. ### 11
**question**: 3a. Is chrome.storage.local written to disk unencrypted?
**answer**: Yes. Chromium keeps each extension's storage.local in a LevelDB database under '<profile>/Local Extension Settings/<extension id>'. The files read (value_store_util.cc, value_store_factory_impl.cc, leveldb_value_store.cc) contain no encryption call. Chrome's own developer guidance says extension storage is not encrypted. Anyone who can read the profile folder (malware running as the user, a backup, a stolen disk without full-disk encryption) can read it.
**verdict**: confirmed
**evidence**: https://chromium.googlesource.com/chromium/src/+/main/extensions/common/constants.h (read through raw.githubusercontent.com/chromium/chromium/main, 2026-10-09), lines 123-126: "// The name of the directory inside the profile where per-extension local settings are stored. ... kLocalExtensionSettingsDirectoryName[] = FILE_PATH_LITERAL(\"Local Extension Settings\");" extensions/browser/api/storage/value_store_util.cc lines 24-27: "case settings_namespace::LOCAL: ... : base::FilePath(kLocalExtensionSettingsDirectoryName);" components/value_store/value_store_factory_impl.cc: "return profile_path_.Append(directory);" and "return std::make_unique<LeveldbValueStore>(uma_client_name, GetDBPath(directory));" (none of these three files contains 'encrypt' or 'OSCrypt'). https://developer.chrome.com/docs/extensions/mv3/user_privacy (source .../extensions/mv3/user_privacy/index.md, updated 2023-06-07): "avoid keeping sensitive user data in the client side of an extension as extension storage is not encrypted."

### 12
**question**: 3b. chrome.storage.session: memory only, cleared when the browser closes, trusted contexts by default?
**answer**: Yes. The session area is held in memory and never written to disk. Its quota is 10 MB (10485760 bytes). ### 13
**question**: 3c. Non-extractable CryptoKey kept in IndexedDB: does it encrypt at rest?
**answer**: A CryptoKey can be stored in IndexedDB, and with extractable set to false no script can export it. That protects against script, not against someone reading the disk. The W3C spec says plainly that key material may be persisted to disk unencrypted. Chromium's structured-clone serializer (used when an object is saved to IndexedDB) writes the raw bytes of a secret (AES) key into the stored value, whatever extractable says. So an AES-GCM-encrypted password sitting next to a non-extractable AES key in the same profile is still readable by anyone with file access. Only a key that is never stored, such as one derived each time from a passkey's PRF output, gives encryption at rest against disk access. Not verified here: whether Chromium encrypts IndexedDB files at rest; nothing read suggests it does.
**verdict**: confirmed
**evidence**: W3C Web Cryptography API, https://w3c.github.io/webcrypto/ (source raw.githubusercontent.com/w3c/webcrypto/main/spec/Overview.html), Key Storage: "In practice, it is expected that most authors will make use of the Indexed Database API ... This allows the storage and retrieval of key material, without ever exposing that key material to the application or the JavaScript environment." Security considerations for developers: "this specification places no normative requirements on implementations as to how the underlying cryptographic key material is stored. The only requirement is that key material is not exposed to script, except through the use of the exportKey and wrapKey operations. In particular, it does not guarantee that the underlying cryptographic key material will not be persisted to disk, possibly unencrypted, nor that it will be inaccessible to users or other applications running with the same privileges as the User Agent. ### 15

## design_implications
- Answering the 401 through onAuthRequired means adding the webRequest and webRequestAuthProvider permissions. That contradicts five standing records: the beethoven-extension CLAUDE.md rule ('Never request cookies, tabs, webRequest ...'), SECURITY.md line 63, the 'Never requested' row of RESEARCH_REPORT.md's permission table, the comment in extension/wxt.config.ts ('webRequest ... must stay absent'), and the store texts. It also arguably breaks 'No automated login of the portal'. Each of those has to change together, by the maintainer's explicit decision, before any code changes. If built, declare both in optional_permissions and request them in the same click as the one portal origin.
- Register the listener only for the one granted portal origin's URL pattern. Answer only when e.isProxy is false, e.scheme is 'basic', the challenger host is the portal's, and e.realm equals the recorded realm ('private' at Wayne State). For anything else return nothing.
- Lockout guard: Wayne State disables an account after five wrong passwords, and reactivation can take three business days. Supply credentials at most once per requestId, and cancel on a second challenge, as FoxyProxy does and MultiPass (max_try = 5) does not. Then mark the stored password as refused and never send it again until the student types a new one. One refused password must stop all automatic sign-in, including the 'Keep my worker running' alarm. Plan for password changes, which take up to 30 minutes to take effect, and for yearly expiry (students, unless the password has 14 or more characters).
- Encryption at rest: Chrome's FAQ 8 asks for AES or RSA at rest, and a non-extractable AES key stored in IndexedDB does not satisfy it against disk access, because Chromium writes the raw key bytes into the stored value. Encrypt the password with AES-GCM under a key derived from the passkey's PRF output, never stored, and keep only ciphertext, salt and the credential ID on disk. Hold the decrypted password or the derived key only in service-worker memory or chrome.storage.session (left at its default trusted-contexts access). That means one Windows Hello or Touch ID prompt per browser session, and again after an extension update or reload.
- The passkey prompt cannot run in the service worker, because navigator.credentials exists only on windows. It must come from a visible extension page, and with the side panel kept that is the side panel. Use the extension ID as the RP ID. A cold start with no open panel cannot unlock; it must wait for the student, which matches today's waiting press.
- Store listing and texts: tick 'Authentication information' in Privacy practices, as 12.0.0 to 15.0.0 did. In the panel, add a prominent disclosure with an unticked box or explicit press before the first save; never pre-ticked. Rewrite PRIVACY.md and LICENSE.txt with their version numbers raised together and TERMS_VERSION to match. Replace the current sentences 'Beethoven never sees them', 'never offers to remember anything' and 'Authentication information: No' (docs/store/LISTING.md lines 163, 210, 276, 286; PASTE.md lines 81, 235-240, 338).
- Wayne State's Strong Password Standard tells users to 'Never save passwords in web browsers or computer programs'. Keep the feature opt-in and off by default, say in the panel that the university advises typing the password each time, and consider asking C&IT (hpc@wayne.edu) before the pilot. 18.0.0's present suggestion that Chrome save the password has the same conflict.
