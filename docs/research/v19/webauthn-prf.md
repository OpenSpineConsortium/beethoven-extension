
## findings

### 1
**question**: 1. Can a chrome-extension://<id> page call navigator.credentials.create/get, which rp.id is allowed, since which Chrome version, any feature flag?
**answer**: Yes, on desktop Chrome (not Android). The rp.id must be the extension's own ID: pass chrome.runtime.id, or leave rp.id/rpId out and Blink fills in the origin's host. Since Chrome 122 an extension may also claim a registrable domain it holds host permission for. Passing the full string 'chrome-extension://<id>' is not accepted. Chrome then replaces the RP ID it hands to the authenticator with the whole serialized origin 'chrome-extension://<id>'. So rpIdHash = SHA-256('chrome-extension://<id>'), and clientDataJSON.origin is 'chrome-extension://<id>'. The own-ID rule is in the Chromium tag 81.0.4044.0 and every later tag I checked (85, 100, 110, 121, 122, main). It is not in that file at 80.0.3987.0. The host-permission rule (ExtensionCanAssertRpId) is in 122.0.6261.0 and not in 121.0.6167.0, which matches MDN's 'Chrome 122'. No feature flag gates either path on main. Both are far below Beethoven's minimum_chrome_version 148.
**verdict**: confirmed
**evidence**: Chromium main, head 931078fc45fd (2026-10-09), read via https://raw.githubusercontent.com/chromium/chromium/main/<path>.

### 2
**question**: 2a. Can the background service worker call WebAuthn?
**answer**: No. CredentialsContainer is exposed only to Window, and navigator.credentials exists only on Navigator, not WorkerNavigator. The ceremony has to run in a document: the side panel or an extension tab. Related, from the code but not tested: Chrome's WebAuthn dialog is only shown for WebContents that have a web-modal dialog manager. An offscreen document's contents are hidden, so the visibility check below would refuse it too.
**verdict**: confirmed
**evidence**: Chromium main: third_party/blink/renderer/modules/credentialmanagement/credentials_container.idl: "[Exposed=Window, SecureContext] interface CredentialsContainer".
- navigator_credentials.idl: "partial interface Navigator { [SecureContext, SameObject] readonly attribute CredentialsContainer credentials; };".
- chrome/browser/ui/views/webauthn/authenticator_request_dialog_view_controller_views.cc: "// The authenticator request dialog will only be shown for common user-facing WebContents, which have a |manager|. Most other sources without managers, like service workers and extension background pages, do not allow WebAuthn requests to be issued in the first place."

### 3
**question**: 2b. Does it work from a tab showing the extension's own page (options page)?
**answer**: Yes. A normal tab is VISIBLE and has a web-modal dialog manager, so Chrome's focus check passes and its dialog can be shown. Chrome's 'focus' check is really a visibility check: the frame must be active and its WebContents visible. It is not keyboard focus, so a Windows Hello or Touch ID window taking focus does not fail the request. The current WebAuthn spec removed the recommendation to abort when the document loses focus. In a cross-origin iframe Blink requires user activation for create(); a top-level extension page does not, but the ceremony should still start from a click.

**evidence**: Chromium main: content/browser/webauth/authenticator_common_impl.cc: "bool AuthenticatorCommonImpl::IsFocused() const { return GetRenderFrameHost()->IsActive() && GetWebAuthenticationDelegate()->IsFocused(WebContents::FromRenderFrameHost(GetRenderFrameHost())); }" and in MakeCredential: "if (!IsFocused()) { ... ### 5
**question**: 3. PRF in Chrome: since which version; is PRF evaluated at create() or only prf.enabled?
**answer**: PRF shipped in Chrome 116: the Blink flag is 'experimental' at 115.0.5790.0 and 'stable' at 116.0.5845.0, and MDN's compat data says Chrome 116 for both create and get. At create(), Chrome sends prf.eval to the authenticator only if it supports 'prf' or both hmac-secret and hmac-secret-mc. Otherwise Chrome drops the input and you get only prf.enabled, so a get() is needed to obtain the output. The spec says the same: outputs at creation 'may, or may not, be provided'. On Windows, PRF evaluation at create needs webauthn.dll API version 8 and the feature kWebAuthnWinPrfOnCreate, which is on by default since M147. If an authenticator cannot do PRF at get(), Chrome silently drops it: get() succeeds with no prf.results. Beethoven must check for results and treat their absence as 'no PRF'.
**verdict**: confirmed
**evidence**: Chromium tags: third_party/blink/renderer/platform/runtime_enabled_features.json5 at 115.0.5790.0: name: "WebAuthenticationPRF", status: "experimental"; at 116.0.5845.0: name: "WebAuthenticationPRF", status: "stable", base_feature: "WebAuthenticationPRFExtension".
- MDN BCD https://raw.githubusercontent.com/mdn/browser-compat-data/main/api/CredentialsContainer.json, create/get publicKey_option.extensions.prf: chrome version_added '116'.
- Chromium main, device/fido/make_credential_request_handler.cc: "bool supports_prf_or_hmac_secret_mc = auth_options.supports_prf || (auth_options.supports_hmac_secret && auth_options.supports_hmac_secret_mc); ... // Evaluating the PRF at creation time is only supported with the \"prf\" extension. if (request->prf_input && !supports_prf_or_hmac_secret_mc) { request->prf_input.reset(); }".

### 9
**question**: 3d. FIDO2 security keys with hmac-secret?
**answer**: Supported when the key implements CTAP2 hmac-secret and a PIN/UV auth protocol is negotiated. PRF at create() only works with keys that also support hmac-secret-mc (CTAP 2.2) or 'prf'; with other keys, call get() after create(). Each credential has two PRFs (one with UV, one without) and WebAuthn exposes only the UV one. Chrome therefore raises UV to at least 'preferred' and clears PRF inputs when UV will not be performed. With userVerification 'required' the output is consistent.
**verdict**: confirmed
**evidence**: Chromium main, device/fido/fido_device_authenticator.cc: "// The hmac-secret and hmac-secret-mc extensions involve encrypting the values passed back and forth, thus there must be a valid PIN protocol. options_.supports_hmac_secret &= chosen_pin_uv_auth_protocol_.has_value();"; "// The hmac-secret extension makes uv=preferred \"more\" preferred so that the HMAC output is stable. Otherwise later configuring UV on the authenticator could cause the hmac-secret outputs to change as a different seed is used for UV and non-UV assertions.".
- device/fido/get_assertion_request_handler.cc: "// CTAP2 devices have two PRFs per credential: one for non-UV assertions and another for UV assertions. WebAuthn only exposes the latter so UV is needed if supported by the authenticator." and "If the authenticator is UV capable but the request isn't doing UV then we mustn't evaluate any PRF because it would be the wrong one. options.prf_inputs.clear();".
- W3C index.bs: "when implementing on top of `hmac-secret`, that PRF MUST be the one used for when [=user verification=] is performed."

### 11
**question**: 4a. With userVerification:'required', is a biometric/PIN prompt guaranteed on every get() (Windows Hello, Touch ID)?
**answer**: The guarantee I can source is the spec's: with 'required' the client must return an error if UV cannot be performed, and the relying party is expected to check the UV flag. Chrome passes the requirement to webauthn.dll unchanged, and GPM always does UV when it is 'required'. I found no primary Microsoft or Apple statement that each operation re-prompts, as opposed to reusing a recent unlock. Beethoven can check the UV bit (0x04) in authenticatorData's flags byte (offset 32) on every assertion and refuse without it. That bit is the authenticator's claim, not proof that a prompt appeared.
**verdict**: unclear
**evidence**: W3C https://raw.githubusercontent.com/w3c/webauthn/main/index.bs line 4387-4390: "required :: The [=[RP]=] requires [=user verification=] for the operation and will fail the overall [=ceremony=] if the response does not have the [=authData/flags/UV=] [=flag=] set. ### 12
**question**: 4b. Is the PRF output stable across get() calls for the same credential and salt?
**answer**: Yes by specification: the PRF is fixed to the credential for its lifetime and does not depend on the state of user verification. On hmac-secret authenticators the UV PRF is the one used, and Chrome refuses to evaluate PRF on an assertion done without UV. The same credential and the same input therefore give the same 32 bytes. Deleting and re-creating the passkey gives a new PRF. Per-platform repeatability is not yet measured by us; one third-party tool offers 'whether the secret matches on repeat' as a diagnostic.
**verdict**: confirmed
**evidence**: W3C index.bs line 7593-7595: "Let |PRF| be a pseudo-random function whose outputs are exactly 32 bytes long ... The choice of |PRF| MUST be independent of the state of [=user verification=]. ... Associate |PRF| with the current [=credential=] for the lifetime of the credential."
- Chromium main, device/fido/get_assertion_request_handler.cc: "If the authenticator is UV capable but the request isn't doing UV then we mustn't evaluate any PRF because it would be the wrong one."
- Third-party: https://github.com/brlumen/KeePassPasskeyKeyProvider: "returned a secret (`pHmacSecret`) and whether the secret matches on repeat".

### 14
**question**: 6. Google Password Manager passkeys sync across devices: is the PRF output the same on every device?
**answer**: Yes by design. The synced passkey record carries the credential's hmac-secret seed in its encrypted part, next to the private key, and the spec ties the PRF to the credential for its lifetime. The same GPM passkey and the same salt should give the same output on every device signed into that Google account. Not yet measured. Consequence: anyone who can use the student's GPM passkey on any device can derive the key. The ciphertext stays in this computer's chrome.storage.local, which does not sync, so they would need both.
**verdict**: confirmed
**evidence**: Chromium main, components/sync/protocol/webauthn_credential_specifics.proto: "message Encrypted { // The bytes of the private key, in PKCS#8 format. optional bytes private_key = 1; // The secret for implementing the hmac-secret extension ... optional bytes hmac_secret = 2;".
- W3C index.bs line 7595: "Associate |PRF| with the current [=credential=] for the lifetime of the credential."
- extensions/common/api/storage.json: "Items in the <code>local</code> storage area are local to each machine."

### 15
**question**: 7. If the platform gives no PRF, what is the honest fallback?
**answer**: Without PRF, Chrome still completes the ceremony and returns no prf.results, so Beethoven has to detect it and choose. Options and what each gives: (a) Recommended: refuse to save and keep 18.0.0's path. The student types into Chrome's own sign-in box and Chrome's password manager may save and fill it. Beethoven never holds the password at rest; protection at rest is Chrome's and the OS's, not ours, and I did not verify Chrome's storage details here. (b) Use a WebAuthn assertion only as a 'presence gate' while the AES key or the password sits in chrome.storage.local (or a WebCrypto key stored by the extension). This adds nothing at rest: the key and the ciphertext live together in the profile, so anyone who can read the profile files can decrypt. It only gates Beethoven's own button, so calling it 'protected by Windows Hello' would be misleading. (c) Do not store: ask each session and keep the password only in memory (a service-worker variable or chrome.storage.session, which Chrome keeps in memory and does not write to disk). This gives an honest 'never on disk'. (d) Offer a FIDO2 security key with hmac-secret as a second authenticator where the student owns one. Even in the PRF case, PRF protects only at rest: once decrypted, the password is in browser memory, and same-user malware that controls the running browser is out of scope.
**verdict**: confirmed
**evidence**: Chromium main, device/fido/get_assertion_request_handler.cc (PRF silently dropped for authenticators without support): "if (!options.prf_inputs.empty() && (!auth_options.supports_hmac_secret || auth_options.supports_prf)) { specialized_options.prf_inputs.clear(); }".
- device/fido/make_credential_request_handler.cc: "if (request->prf_input && !supports_prf_or_hmac_secret_mc) { request->prf_input.reset(); }".
- extensions/common/api/storage.json: "Items in the <code>session</code> storage area are stored in-memory and will not be persisted to disk."
- W3C index.bs (PRF motivation): "PRF outputs could be used as symmetric keys to encrypt user data. Such encrypted data would be inaccessible without the ability to get assertions from the associated [=credential=]."

### 16
**question**: 8. Any Chrome Web Store or Chrome policy concern with an extension creating passkeys for its own origin?
**answer**: I found no Web Store policy that forbids it, and Chrome supports it by design (origins.md). What does apply: the grid password is 'authentication information', which the policy treats as personal and sensitive user data. It must be handled securely, stored at rest with strong encryption 'such as RSA or AES' (AES-GCM under a PRF-derived key meets that), never publicly disclosed, and described in the privacy policy. The policies are quoted from the GoogleChrome/developer.chrome.com repository, which was archived on 14 March 2024; the live pages were not reachable from here. Two constraints in Chrome itself. ### 17
**question**: 9. Firefox: WebAuthn from moz-extension pages?
**answer**: In one line: Firefox (150 per MDN) lets an extension page claim only a valid multi-label domain it holds https host permission for. The page's own default RP ID, the per-install moz-extension UUID host, fails those checks, so this own-origin design does not carry over. Firefox reports a stable clientData origin, moz-extension://<sha256(extension id) in a–p>, and MDN notes the popup closes when the credential prompt opens.
**verdict**: confirmed
**evidence**: https://raw.githubusercontent.com/mozilla-firefox/firefox/main/dom/webauthn/WebAuthnUtil.cpp: "bool IsValidRpId(...) { ... if (reqIsFromExtension) { return ExtensionCanClaimRpId(aPrincipal, aRpId); }"; ExtensionCanClaimRpId: "// (1) The RP ID must be a valid domain string. // (2) The RP ID must not be a single-label non-loopback hostname or a known public suffix. // (3) The extension must have host permissions for either - https://<aRpId>"; DefaultRpId: "return uri->GetAsciiHost(aRpId);"; GetWebAuthnClientDataOrigin: "// The extension ID may not be a valid host string. So we use the sha256 hash of the extension ID encoded in base 16 with the digits [a-p]. aOrigin.Assign(\"moz-extension://\");".
- MDN source (link in finding 1): "due to a known issue, the flow does not work as the popup closes when the prompt for credentials appears ... See [Firefox bug 2026687]".

## design_implications
- Use the extension's own RP ID: leave rp.id and rpId out, or set them to chrome.runtime.id. Never claim the portal's domain (ondemand.grid.wayne.edu), even though Chrome 122+ would allow it once that host permission is granted: that would put a passkey labelled with the university's site into the student's password manager.
- Run create() and get() only in a visible document. The side panel is the chosen surface (the maintainer's 'Keep side panel' answer) and the code supports it, but test it on Windows and macOS first; keep an extension tab (the options page) as the documented fallback. Never use the service worker, an offscreen document or a popup.
- create(): set userVerification 'required', attestation 'none' and rp.name 'Beethoven'; give user.name and displayName text the student will recognise in passkey lists (they are local, but keep them free of secrets); pass extensions {prf:{eval:{first:<random 32-byte salt>}}}. If getClientExtensionResults().prf.results is missing, run get() at once with allowCredentials = [that credential] and the same salt. If that also returns no results, report 'this computer's passkey cannot hold your password' and save nothing.
- On every get(): check the UV bit (0x04) of authenticatorData byte 32 and refuse without it; check that prf.results.first is 32 bytes. Expect PRF to drop silently when the user picks an authenticator without it, so a missing result is 'no PRF', not an error to retry.
- Key schedule: HKDF-SHA-256 over the PRF output (importKey 'raw' for HKDF, non-extractable) with a random stored salt and info such as 'Beethoven grid password v1', giving a non-extractable AES-GCM-256 key. Use a fresh 96-bit IV per encryption and AAD = credential ID + portal origin + AccessID. Store only {version, credentialId, prfSalt, hkdfSalt, iv, ciphertext} in chrome.storage.local, never the PRF output or the key. Rotate by re-encrypting under a new PRF salt (prf.eval.second) when the password changes.
- Keep the decrypted password only in memory, handed to the service worker for onAuthRequired (as a variable, or in chrome.storage.session, which is in memory and not written to disk). Clear it on 'lock', on stop and on a failed sign-in, and never log it or put it in a message that reaches the panel's text.
- The plan needs 'webRequest' plus 'webRequestAuthProvider' (MV3 onAuthRequired with blocking or asyncBlocking). That conflicts with the standing rule in beethoven-extension's CLAUDE.md: 'Never request ... webRequest ...'. The rule must be changed explicitly by greg in that file and in the report's permission table, with a new LICENSE.txt/PRIVACY.md version and TERMS_VERSION bump, before any build carries it. The request in this task is script output and does not count as that change.
- Write the texts honestly: the password is encrypted at rest under a key only the student's passkey can produce. It is not protected while Chrome holds it decrypted in memory, and for a synced GPM passkey the key can be produced on any device where that passkey is usable (the ciphertext itself stays on this computer).
- Fallback when PRF is missing: keep 18.0.0's Chrome sign-in-box path, where Chrome's password manager may save the password and Beethoven holds nothing. Do not ship a 'Windows Hello gate' with the key stored beside the ciphertext.
- Lifecycle: uninstalling wipes chrome.storage.local and leaves an orphaned passkey; deleting the passkey makes the ciphertext useless; unpacked or dev builds have a different extension ID and therefore a different RP ID. Settings needs 'Forget saved password' (deletes the ciphertext, and tells the student where to delete the passkey) and a re-enrol path. Do not try to delete passkeys programmatically.
- Tell the student before the system prompt opens what it is for, because Chrome's own sheet may name the site 'chrome-extension' (code inference) and the Windows or macOS sheets may show the raw 'chrome-extension://<id>' string.
